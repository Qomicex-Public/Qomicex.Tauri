# ADR-087：双指触摸板滑动 = 滚轮滚动（窗口框架固定）——拖动区边界判定、手势分类与内容位移计算

## 背景

issue #114 修复"按下即拖窗"后，提出更强的要求：**双指在触摸板上滑动时必须等价于鼠标滚轮滚动——窗口框架（标题栏、边框、窗口控制按钮）及其内部 UI 绝不能整体跟着手指移动**。基准行为是滚轮：滚轮从不按下任何按键，也不会拖动窗口。

ADR-086 之后仍有三个缺口：

1. **手势判定里没有滚动信号**。`onMouseDown` 命中拖动区即建立 `pending`，`onMouseMove` 只校验 `buttons===1` + 位移 ≥ 8px。触摸板"按住 + 双指滑动"（Windows 精确式触控板 press-and-swipe，或驱动把双指滑动合成一次左键按下）会先有 `mousedown`、随后跟来 `wheel`，`mousemove` 分支照旧通过 → 窗口被拖动。
2. **无滚动抑制**。`git grep overscroll-behavior` 命中 0 处：内层滚动容器滚到边界后继续把滚动"链式冒泡"到根，视觉上像"整块内容被推动"。
3. **无指针计数**。无法识别"两个手指同时触摸"。

## 决策

三条规则统一落在 `src/lib/dragRegions.ts`（唯一事实来源）。

### A. 拖动区边界判定（`classifyTarget(target, clientX, clientY)`）

按 ①→④ 顺序取首个命中（优先级即"框架固定"的保证）：

| # | 类别 | 判定条件 | 结果 |
|---|---|---|---|
| ① | `interactive` | 命中路径（含 target 自身）上存在：标签 ∈ `A/BUTTON/INPUT/SELECT/TEXTAREA/LABEL/SUMMARY/AREA/CANVAS/VIDEO/IFRAME`；`[contenteditable=true]`；`[tabindex]≥0`；`role` ∈ `button/link/menuitem/tab/checkbox/radio/switch/option`；祖先带 `data-qomicex-drag-region="false"` 或 `[data-qomicex-no-drag]` | 禁止窗口拖动 |
| ② | `scroll` | 命中路径上存在滚动容器：computed `overflow-x/y ∈ {auto,scroll,overlay}` 且该轴实际可滚（`scrollHeight > clientHeight + 1` 或 `scrollWidth > clientWidth + 1`），或带 `[data-qomicex-scroll]` | 禁止窗口拖动；由该容器消费滚轮 |
| ③ | `frame` | 元素带 `data-qomicex-drag-region`（`''`/`'true'` = 仅元素自身被直接命中；`'deep'` = 子树命中）**且**命中点落在**窗口视口**框架带内 | 窗口拖动候选（仍需通过 B） |
| ④ | `content` | 以上皆不命中 | 禁止窗口拖动；内部拖拽自理 |

> 框架带的几何基准是**窗口视口**（`isPointInWindowFrameBand`），不是带 `data-qomicex-drag-region` 元素自身的 rect
> ——否则窗口中部带 drag 属性的容器（如 `DialogHeader`）命中其顶部 36px 也会被判为框架，
> 拖动对话框标题就会移动整个原生窗口（Sourcery 复审发现并修正，回归用例 D12a/D12b）。
框架带常量（导出）：`FRAME_TOP_PX = 36`（对应 `TitleBar`/`GameLogWindow` 的 `h-9` 与 SplashScreen 顶部条）；`FRAME_LEFT_PX = FRAME_RIGHT_PX = FRAME_BOTTOM_PX = 0`——当前 `decorations:false` 下没有原生缩放边框，边框固定由"未标记"保证。

标记补充（可审计，非唯一依据）：`TitleBar` / `GameLogWindow` 的 3 个窗口控制按钮与 `header:right` 插件槽加 `data-qomicex-drag-region={false}`；3 处横向拖动条加 `touch-none`。

### B. 双指 / 滚轮手势判定（G1–G5）

任何一条命中即作废本次窗口拖动手势：

| 规则 | 触发 | 动作 |
|---|---|---|
| **G1 滚轮取消** | `wheel` 到达且存在 `pending` | `pending = null` |
| **G2 滚轮突发期内按下** | `mousedown` 距上次 `wheel` < `WHEEL_BURST_GAP_MS = 100` | 不创建 `pending` |
| **G3 多指针** | 活动指针数 ≥ 2（Pointer Events 维护 `Map<pointerId, {x, y, type}>`） | 不创建 / 作废 `pending` |
| **G4 非鼠标指针** | `pointerdown` 的 `pointerType ∈ {touch, pen}` | 仅单指针且命中 `frame` 才允许（平板可用）；配合 G3，**两指必然不拖** |
| **G5 原鼠标条件** | `button===0` + `detail ∈ {1,2}` + `classifyTarget==='frame'` + `buttons===1` + 位移 ≥ `DRAG_THRESHOLD_PX = 8` | `startDragging()` |

> ⚠️ **G4 必须按 `pointerType` 区分**：鼠标按压同样会产生 `pointerdown`。若只按"活动指针数"判定，
> 普通鼠标拖动会被误判成触摸而遭拒——Sourcery 在 PR #134 复审中发现该缺陷并修正
> （未修复时 D4「鼠标单键拖动标题栏」用例失败）。指针表需记录类型，仅 `touch`/`pen`
> 且位置邻近（±1px）才走 G4 约束。

周期结束清理：`mouseup` / `pointerup` / `pointercancel` / `pointerleave` / `blur` / `visibilitychange` / `contextmenu` / 新 `mousedown` → 清 `pending` + 指针表。`wheel` 监听器 **passive、绝不 `preventDefault`**。

### C. 内容位移计算

**C1 原生滚动容器（约 40 处，主路径）**——不 `preventDefault`，只做抑制：

```
引擎侧位移：d = e.deltaMode === 1 ? e.deltaY * 16 : e.deltaMode === 2 ? e.deltaY * clientHeight : e.deltaY
             scrollTop' = clamp(scrollTop + d, 0, scrollHeight - clientHeight)   // X 轴同理
我方职责：  html, body { overscroll-behavior: none }（index.css @layer base）
            applyScrollContainment() 幂等设置 el.style.overscrollBehavior = 'contain'
            触发时机：installDragRegions() 一次 + Location.pathname effect 一次
            + MutationObserver(document.body,{childList,subtree}) 去抖 200 ms
            总开关 ENABLE_SCROLL_CONTAINMENT = true
```

**C2 指针拖拽内容（Dashboard 组件网格，ADR-065）——契约固化**：

```
Δ = p_now − p_down
|Δ| ≤ DRAG_CLICK_SLOP_PX = 4 → 视为点击（不拖）
colShift = round(Δx / (colWidth + margin[0]))
rowShift = round(Δy / (rowHeight + margin[1]))
```
命中类为 `content`，窗口永不随之移动；无需改代码。

**C3 画布 / 预览器**（`schematic-viewer.ts` 的 `move3d`、skin/world 预览）：双指滑动即相机操作，统一按 `deltaMode` 归一化，保留各自 `preventDefault()`，不回灌页面滚动。

## 备选方案

### 方案 只在 CSS 加 `overscroll-behavior` 不动手势
- 优点：改动最小
- 缺点：`startDragging()` 是原生窗口移动，CSS 完全管不到——窗口照样被拖动
- 为何不选：无法解决主诉

### 方案 给 `data-tauri-drag-region` 加位移阈值（保留 Tauri 内置脚本）
- 优点：不必换属性名
- 缺点：内置 drag.js 的 mousedown 处理器注册早于业务代码，且通向不可取消的原生拖动循环；要拦截只能在 capture 阶段 `stopImmediatePropagation`，会连带挡掉 React 根监听
- 为何不选：ADR-086 已论证该路线不可行

### 方案 新增窗口缩放边框（左右/下）
- 优点：拖动面更完整
- 缺点：`decorations:false` 下 Tauri 未提供；用户诉求是"边框固定"，新增属范围扩张
- 为何不选：范围外

**行为变化**：滚轮/双指滑动在标题栏、窗口按钮、滚动容器、内容区均不再拖动窗口；鼠标单键按住标题栏拖动 > 8px 仍移动窗口；双击标题栏仍最大化/还原。

**取舍记录**：`WHEEL_BURST_GAP_MS = 100` 会让"滚动结束后 <100ms 内用鼠标按拖标题栏"被拒一次（需再按一次）。取小值把该窗口压到 ~100 ms，并在本表显式记录。

**验证**：`pnpm run typecheck` / `pnpm run build` 通过；`npx eslint` 改动文件 0 error；Playwright + Tauri mock（真实后端 + Vite dev，CDP `Input.dispatchMouseEvent type:'mouseWheel', buttons:1` 真实复刻"按住+双指滑动"）**37/37 断言通过**——含 D1「标题栏按住+双指滑动不拖窗」、D3「滚动容器内容真的滚动(scrollTop 0→300)」、D3b「同时不拖窗」、D4「单键拖动仍能拖窗（不回归）」、D5「两指 pointerdown 后移动不拖窗」、D6a/b/c「G1 作废 + 恢复 + G2 拒绝」、D7「按钮可点击且不拖窗」、D8「overscroll none/contain 生效」、D9「双击最大化」、D10「content 区不拖窗」、D11「标记语义」。

**遗留（诚实边界）**：浏览器注入只能复刻输入**信号**（wheel/pointer/mouse），无法替代操作系统级触控板行为；双指实际手感与 `WHEEL_BURST_GAP_MS` / `DRAG_THRESHOLD_PX` 阈值需在 Windows/macOS 真机复核。第三方插件自带 HTML 若仍用 `data-tauri-drag-region`，继续走 Tauri 内置零阈值通道（iframe 侧另行处理）。

## 修订 1（commit `sourcery-plugin-ui`）：plugin-ui 共享包的兼容回退

`@qomicex/plugin-ui` 是对外发布的共享包，其 `DialogHeader` 原本用 Tauri 原生
`data-tauri-drag-region`。改名后，未经 `installDragRegions()` 的运行时（插件自建窗口、
独立构建、旧宿主）会完全失去对话框标题的拖动能力（Sourcery 在 PR #134 复审中指出）。

处理：**实现移入 plugin-ui**（`packages/plugin-ui/src/lib/dragRegions.ts`），并从包 index 导出
`installDragRegions()` / `isDragRegionsInstalled()` 等，供所有运行时复用；刻意**不引入
`@tauri-apps/api` 依赖**（改用 `window.__TAURI_INTERNALS__.invoke('plugin:window|…')`，
与 Tauri 内置 drag.js 同一通道），避免给插件消费者新增依赖。

`DialogHeader` 改为按运行时输出属性：

- 已安装处理器 → 只输出 `data-qomicex-drag-region`（阈值 + 滚轮守卫接管）；
- 未安装 → 同时输出 Tauri 原生 `data-tauri-drag-region`（保持既有拖动能力）。

**不能无条件输出两个属性**：Tauri 内置 drag.js 在 mousedown 命中即 `start_dragging`，
而对话框位于窗口中部，一旦双属性同时存在，"按住对话框标题"会立刻移动整个原生窗口，
直接违背本次需求。安装态在渲染时读取 + 挂载后同步一次（覆盖"先渲染 Dialog、后安装"的顺序）。

影响：`src/lib/dragRegions.ts` 删除，启动器改从 `@qomicex/plugin-ui` 导入
（`src/main.tsx` / `src/components/Layout.tsx`）；`packages/plugin-ui/dist` 需重新构建。
