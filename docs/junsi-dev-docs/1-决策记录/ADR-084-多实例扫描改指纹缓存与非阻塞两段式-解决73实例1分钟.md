# ADR-084 多实例扫描慢的根因与修复：版本扫描指纹缓存 + 非阻塞 + 两段式扫描

- 状态：已接受
- 日期：2026-09-23
- 影响面：启动器本地后端（`endpoints/version.rs`、新增 `services/scan_cache.rs`、
  `state.rs`、`services/instance.rs`）、core submodule
  （`qomicex-core-rust/src/util/version_json.rs`）、启动器前端
  （`api/versions.ts`、`types/index.ts`、`pages/Instances.tsx`）、
  API 文档（`3-API规范/API列表.md`）

## 症状

73 个游戏实例的目录，进"多游戏实例"页要 1 分多钟才出列表。

## 根因：慢的不是目录遍历，是每个实例的 client jar 解析

`GET /api/versions/scan` 对每个版本目录调用 `resolve_game_version()`，
其第 1 级是打开 `versions/{name}/{name}.jar` 读 `version.json`；
读不到走 `Minecraft.class` 常量池；再不到就 **`std::fs::read(jar_path)`
整包读入 + SHA1**（`GameVersionHelper.FromJar` 的第 4 级已知 SHA1 映射表）。
这个计算**每次打开实例页都全量重做、零缓存**——而每个版本目录里确实躺着完整
client jar（`qomicex-core-rust/src/services/installers/forge_base.rs:622`
明确写 `versions/{version_dir_name}/{version_dir_name}.jar`）。

实测（本机，`target/debug`，73 个合成实例，jar ~10MB/个）：

| 场景 | 耗时 |
|---|---|
| 只读 `{name}.json` + `detect_loaders`，不碰 jar | **32–160 ms** |
| jar 内含 `version.json` | 1.6–2.1 s |
| jar 无 `version.json` → 整包 SHA1（1.24 GB） | 11.4 s（OS 缓存热）/ **37.6 s（冷）** |
| 规范化后本次验收（73 × 17.4MB = 1.27 GB，全走 SHA1） | 3.7 s |

> 73 个真实整合包（GTNH 类 30–60MB/个，1.5–4.5 GB jar）+ 冷盘缓存 + 老 Forge 包
> 命中 SHA1 全包读路径 + 每次进页面重扫 = 用户看到的"1 分多钟"。
> release 构建 SHA1 更快（x86/x86_64 走 SHA-NI，见决策 3），
> **但磁盘读 jar 的开销不变**。

附带的三处小开销（其中图标与 `save_to_file` 见决策 5，已一并优化）：
- 图标：73 × 120KB PNG → base64 **11.4 MB** 响应体，前端再原样 POST 回
  `/instance/sync-scan`（又来 11.4 MB），往返 ≈0.7 s；
- `InstanceService::save_to_file()` 用 `to_string_pretty` 把含图标的 ≈10MB
  `instances.json` 每次同步都全量重写；
- `scan` handler 是纯阻塞 I/O 的 `async fn`，扫描期间占着 tokio worker。

## 决策 1：按"版本目录"做文件指纹缓存（`services/scan_cache.rs`）

目录遍历仍每次全做（73 次 `metadata` 约 1ms，负责发现新增/删除/改名），
但每个版本目录只用 `fs::metadata` 取 `{name}.json` / `{name}.jar` 的
`(长度, mtime)` 指纹：

- 指纹与缓存一致 → **完全不打开 jar**，直接复用 `game_version` / `loaders`；
- 指纹不一致/缺失 → 走完整 `resolve_game_version` + `detect_loaders`，写回缓存。

JSON 仍每次解析（约几十毫秒）：响应的 `name` 取自 JSON 的 `id`（可能与目录名
不同），且 `detect_loaders` 只读 JSON。两者都不涉及 jar，是"便宜的那一半"。

持久化：`{base_dir}/data/version-scan-cache.json`，临时文件 + rename 原子替换，
仅在有改动时落盘；启动时解析失败/格式版本不匹配按"无缓存"处理（不影响功能，
只影响首扫）。自带清理：版本目录消失 → `prune_versions` 淘汰；
整个 `versions/` 没了 → `drop_game_dir`。

**为什么用指纹而不是显式 `invalidate`**：安装/卸载/改名/整合包导入路径分散
（`instance.rs` 的 create/update/rename、`install_service.rs`、`modpack.rs`、
MultiMC 导入各有一套），显式失效迟早漏一个——漏一次就是永久显示错版本号。
指纹方式对调用方零侵入，改名/换 jar/补文件天然失效。


**指纹覆盖哪些文件**：`{name}.json` + **`effective_jar_path` 实际会打开的那个 jar**。
`inheritsFrom != id` 时 jar 级探测读的是 `{inheritsFrom}.jar` 而不是 `{name}.jar`，
所以指纹必须记前者。这条是自查中发现并修掉的漏失效（get/put 两侧的 jar 路径假设
一旦不一致，旧值会被永久命中）；现在指纹由调用方算好后作为入参传给 `get`，
缓存服务自己不再拼路径。回归测试见 `miss_when_inherits_jar_changes`。
**已知取舍**：同一文件系统 mtime tick 内被改写为**同长度**的 jar 会读到旧值。
实际不可复现（NTFS mtime 精度 100ns；写 jar 必然改变长度）。逃逸口：
删 `{base_dir}/data/version-scan-cache.json` 强制全量重算。

收益（本次验收，73 实例 / 1.27 GB jar）：

| | 冷缓存 | 热缓存 |
|---|---|---|
| `?mode=fast` | 126 ms | **19–22 ms** |
| `?mode=full` | 1211 ms | 19 ms |

61× / 1206 ms → 19 ms。

## 决策 2：扫描整体移出 tokio 运行时

`scan` handler 包进 `tokio::task::spawn_blocking`，同步扫描的磁盘 I/O 不再
占 tokio worker。实测：一次 3.7 s 的阻塞扫描期间，`/api/health` 的最大延迟
**37 ms**（改造前会被同一个 worker 上的扫描堵住）。

## 决策 3：SHA1 流式化（core submodule）

`qomicex-core-rust/src/util/version_json.rs` 的 `from_jar` 第 4 级由
`std::fs::read(jar_path)` 整包读入改为 **64 KiB 缓冲流式哈希**：
- 峰值内存与 jar 大小解耦（25–60MB jar 不再整包进堆，73 个的峰值从 GB 级降到 <1MB）；
- 复用同一个打开的 `File`（`try_clone` 复制句柄给 `ZipArchive`，SHA1 用另一份
  并显式 `seek(0)`）——不再二次打开、二次读；
- `to_hex` 与原先 `format!("{:02x}")` 逐字节等价（core 43 个用例全绿）。

**关于 sha1-asm / SHA-NI 硬件加速（立项时的一项，已核实）**：不需要做 ——
它已经是**默认路径**。`sha1` 0.10.7 的 `src/compress.rs` 用 `cfg_if!` 选择实现：
`force-soft` → `soft`，否则在 **x86/x86_64 上一律编译 `compress/x86.rs`**，
里面 `cpufeatures::new!(shani_cpuid, "sha", "sse2", "ssse3", "sse4.1")` 运行时检测，
命中即走 `#[target_feature(enable = "sha,sse2,ssse3,sse4.1")]` 的 SHA-NI 内核。
也就是说 `asm = []` 是个**空特性**（旧 crate 遗留），加它对 0.10.7 没有任何作用；
而 `force-soft` 谁都没开 —— 开了只会把硬件路径关掉。
实测（`sha1bench` 临时 crate，16 MiB × 8，release）：

| 构建 | 吞吐 | digest[0] |
|---|---|---|
| 默认 | **2238.5 MiB/s** | 0x39 |
| `force-soft` 对照 | 910.2 MiB/s | 0x39 |

摘要逐字节一致、只是慢 2.5 倍 —— 硬件确实在用。
（当初"未采纳"的另一个理由是 `sha1-asm` 会打断 `aarch64-apple-darwin` release 构建，
这条依然成立。）

**因此真正该做的是别把硬件路径挡在"整包读进堆"后面**。`from_jar` 的 64 KiB 流式改写
（本节上文）解决的是扫描路径；整合包导出还有两处同样的（`services/modpack_export.rs`
的 `mr_reverse_lookup` 与 MultiMC 导出的反查），原先都是 `fs::read` 整个 mod jar 再
`sha1_hex(&bytes)` —— 单个 mod 动辄几 MB，几百个 mod 会让峰值内存跟着最大的那个线性涨。
改为新增 `sha1_file_hex(path)`（64 KiB 缓冲 + `hasher.update`），
`sha1_hex` 降级为 `#[cfg(test)]` 的参照实现（两个新用例断言流式与整包摘要逐字节一致，
含 0 字节 / 小于 1 个缓冲 / 跨 3 个缓冲 / 非对齐边界，以及空文件与缺失文件的语义）。

## 决策 4：两段式扫描，首屏不等 jar

`ScanQuery` 新增 `mode`（`fast` 默认 / `full`），响应新增 `refineRequired`：

- `fast`：命中缓存者直接复用；未命中者只走 JSON 链
  （`resolve_game_version_from_json`，即原回退链去掉第 1 级）→ 毫秒级出列表；
  存在未命中者时 `refineRequired=true`。
- `full`：给未命中者补算 jar 级结果并写缓存，`refineRequired=false`。

语义上保留了"jar 级最准"的回退顺序：jar 仍是第 1 级，只是**它只在命中或
显式 full 时被打开**。`resolve_game_version` 拆成
`game_version_from_jar` + `resolve_game_version_from_json`（纯重构，
`resolve_game_version` 签名与调用方不变，connector `host_port` 不受影响）。

前端 `doScan`（`pages/Instances.tsx`）改为两段：
1. `scanVersions(dir, 'fast', onMeta)` 渲染列表 —— 用户立即看到 73 个实例；
2. `onMeta` 拿到 `refineRequired`，为 true 时再发 `scanVersions(dir, 'full')`
   回填并 `syncScan` 一次。沿用现有 120s 长超时，不阻塞首屏。

`onMeta` 是可选第三参：`scanVersions` 的返回值仍是 `ScannedVersion[]`，
**hook 契约（`hook:scanVersions`）不变**，插件的 before/after 行为不受影响。

**未采纳**：计划里的"兜底设置项 `scanVerifyJarFirst`"。加了必然要动
`settings.rs` + Settings UI + i18n submodule（7 语言键），而指纹缓存已经让 jar
路径每个版本目录最多跑一次，"我要快不要准"的诉求没有实际场景；
逃逸口（删 `version-scan-cache.json`）足够。若后续有需求再加。

## 决策 5：`instances.json` 紧凑序列化

`save_to_file()` 由 `to_string_pretty` 改为 `to_string`。含 base64 图标时
该文件 10MB+，pretty 的缩进/换行让每次同步的写盘时间和体积都明显放大
（验收样本 24 KB 紧凑 / 同内容 pretty 约 +30%）。

### 图标链路（73 × 120KB base64，11.4 MB×2 往返）——已优化

**根因**：`resolve_pcl_icon` 的产出会被搬四次：`/versions/scan` 响应体 → 前端
`syncScan` 请求体 → `instances.json` 落盘 → `GET /api/instance` 响应体，
而图标在 UI 里最大只渲染到 **16×16 CSS px**（`Instances.tsx` 网格 `h-16 w-16`；
列表 12、详情 10/8、仪表盘 10/12）—— 512×512 的源图有 32 倍像素冗余。

**改法**（`util/pcl_icon.rs` 重写）：
- 生成 data URI 前把 PNG 缩到 `ICON_MAX_EDGE = 128`（= 最大渲染尺寸 ×8，
  覆盖 4× DPR）：`png` crate + `Transformations::normalize_to_color8()` 统一成
  8bit 四色型，面积平均（box filter）缩放，RGBA 先预乘再平均、再取消预乘
  （否则透明边缘会产生彩色晕环）。**输出仍是 `data:image/png;base64,...`**，
  `InstanceIcon` 一行未改，其余形态（jpg/webp/gif）原样返回。
- `(长度, mtime)` 指纹 + 进程内缓存（上限 2048 条后整体清空）：每次扫描过 73 个
  目录不再重复解码/编码；文件一变指纹即失效。
- 安装/导入路径也归一并落盘（`modpack.rs` 的 MultiMC 导入与 `install-direct`），
  否则只有扫描路径缩小，`instances.json` 里存的全尺寸图标照样 10MB+。

**有意保留的不对称**：`write_pack_icon`（`modpack.rs` 两处调用）仍把**原图**写到
`versions/{name}/icon.png`，只把缩略图放进 `instances.json` / API 响应。
原图是用户的资产，磁盘上留全分辨率、链路里只传缩略图，将来 UI 换成大图时不必重新
导入整合包；`resolve_pcl_icon` 读到该文件时会自行缩小。别"顺手"把落盘也改成缩略图。

**顺带修掉一个功能性 bug**：`/api/instance/sync-scan` 没配 `DefaultBodyLimit`，
axum 默认 2MB 上限 —— 11.7MB 的回传请求直接 **413**，而前端 `catch {}` 把它吞掉，
表现为实例列表/分组静默不更新。该路由改为显式 64MB。

**仍然未采纳**：把图标从 base64 data URI 改成落盘文件 + 路径。需要新增静态文件
路由 + `InstanceIcon` 的 URL 形态 + `icon_data` 语义变更，影响面（`/api/instance`
持久化、插件 hook 返回的实例对象）远大于现在的收益；同理也没有从
`instances.json` 去掉 `icon_data` 持久化（重启后 `GET /api/instance` 就要重新
解析所有图标）。

## 决策 6："跳过 JAR 级探测"设置项（`scan_skip_jar_probe`）

决策 4 里"未采纳 `scanVerifyJarFirst` 兜底设置项"的理由是"缓存已让 jar 每个版本
目录最多跑一次"。真实目录结构下这个前提会破：GTNH 类整合包没有 `version.json`、
只有 30–60MB 的 jar，走 SHA1 全包读；而**指纹未命中时 fast 也会付这个钱**
（fast 返回后前端按 `refineRequired` 补发 full）。几十 GB 的整合包目录首次导入
仍是分钟级，用户想要一个"我就是要快"的明确开关。

因此新增 `scan_skip_jar_probe`（`settings.rs` + Settings UI + 7 语言 i18n）：

- **语义**：设置**优先于请求参数**。开启后请求里的 `mode=full` 被静默降级为 fast，
  `refineRequired` **恒为 false**（否则前端会拿着恒真的 `refineRequired` 反复发注定
  被降级的 full 请求，形成无限补扫循环）。
- **作用范围**：只有 `/api/versions/scan` 读它。启动实例、安装/卸载、整合包导入导出、
  联机等其它路径完全不读这个设置。
- **对现有行为的影响**：已有指纹缓存继续复用（缓存命中不打开 jar，是纯赚），
  只是不再计算新的 jar 级结果。
- **代价（重要，与"审查后修正"第 2 条的前提相反）**：那条修正是靠"前端只在 full 段
  之后才 syncScan"来避免 fast 段的猜测值落盘。本开关把 `refineRequired` 压成 false，
  前端于是跳过 full 段、**直接拿 fast 段结果去 syncScan** —— 而后端
  `sync_scan` → `list_existing` → `sync_from_disk` 会把扫描到的 `game_version`
  写进 `instances.json`（`save_to_file()`）。
  也就是说开启后 **JSON 链的值会被持久化**。这正是本开关想要的语义（不开 jar，
  JSON 链的值就是最终答案），但它确实打破了"猜测值不落盘"这条不变量：
  关掉开关即可恢复。JSON 字段齐全的版本（现代 Forge/Fabric/NeoForge、vanilla）结果
  完全一致；JSON 缺字段的版本（部分手工整合包、GTNH 类）`gameVersion` 可能退化成
  `inheritsFrom` 或目录名，而这个值会被记住。jar 里的版本号才是权威值，
  所以默认关闭（`None`/`false`）。

## 审查后修正（对抗性自查 + code-reviewer 子代理）

实现完成后做了两轮审查，其中三条是会导致错误数据/功能回归的真实缺陷，均已修复：

1. **给 hookable 方法传函数会打穿插件 hook 管线**（`src/api/versions.ts`）。
   `hookable()` 把入参原样 `postMessage` 给插件 hook，而**函数无法结构化克隆**。
   最初版本用 `onMeta(meta)` 回调把 `refineRequired` 传出去 —— 任何注册了
   `hook:scanVersions` 的插件（文档承诺的扩展点）都会让 `postMessage` 抛
   `DataCloneError`，整条 hook 管线 reject，最终实例页渲染空列表。
   改为把 meta 以**不可枚举属性**挂在返回的数组上（`versions.scanMeta`）：
   返回值仍是 `ScannedVersion[]`，hook 契约不变，postMessage 也只看到纯数组。

2. **fast 段的"猜测值"会落进 `instances.json`**（`endpoints/version.rs` 的
   `fix_instance_*` + 前端 `syncScan`）。JSON 链的 `gameVersion` 可能只是 `inheritsFrom`
   甚至目录名；一旦 full 段超时/失败，脏数据就永久留在磁盘上，而下游
   `gameVersion` 有真实语义（Java 版本选择、联机实例匹配）。
   修法：① 后端 `fix_instance_game_versions/loaders` 只在 `full` 段调用；
   ② 前端 fast 段**不调 syncScan**，只有"没有待校正条目"（即全部缓存命中、
   值已验证）或 full 段跑完后才落盘。顺带修掉 `reqId` 在 fast 返回后才取的竞态。

3. **指纹跟踪的 jar 与真正打开的 jar 不是同一个文件**（`endpoints/version.rs`）。
   `inheritsFrom != id` 时 jar 级探测打开的是 `{inheritsFrom}.jar`，而指纹只记
   `{name}.jar` —— 换父 jar 后 `get()` 永久命中旧值。
   修法：新增 `effective_jar_path()`，指纹覆盖它真正会打开的那个文件，
   并由调用方把指纹算好后传给 `get()`，缓存服务不再自己拼路径。

其余修正：工作线程 panic 不再静默丢弃整块版本目录（`tracing::error!` 留痕）；
未知 `mode` 返回 400 而非静默按 fast 处理；`flush()` 的临时文件名带 pid
（并发 flush 不再互相覆盖）；`instances.json` 与扫描缓存都改为 tmp+rename 原子替换
（原先 `save_to_file` 直写，进程被杀会截断 → `load_from_file` 返回空表 → 全部实例记录丢失）；
从 `CachedVersion` 里删掉只写不读的 `loaders` 字段（`detect_loaders` 只读 JSON、
毫秒级，命中路径上本就重算，缓存格式版本随之升到 2）。

## 已知限制 / 后续

1. **core submodule 改动需单独推送**：`qomicex-core-rust` 的
   `perf(core): JAR 版本识别 SHA1 改为流式哈希并复用文件句柄`（commit `4b4fad9`）
   已随本 ADR 首个提交（`a097fba`）把主仓库的 gitlink 指到它，但该提交本身还只在
   本机 core 仓库（`origin/main` 在 `acaf31c`）。合并前需先推送，否则 release CI
   递归 checkout 子模块会拿不到 `4b4fad9`：
   ```bash
   git -C qomicex-core-rust push https://github.com/Qomicex-Public/qomicex-core-rust.git HEAD:main
   ```
   （本环境 SSH port 22 被关闭，必须用显式 HTTPS URL。）
   `prune_versions` / `drop_game_dir` 兜底；清理 `version-scan-cache.json` 可手动重置。
2. **跳过 JAR 级探测是以精度换速度**（决策 6）：开启后 JSON 缺字段的整合包
   `gameVersion` 可能退化成 `inheritsFrom` / 目录名。默认关闭；需要时用户自己开。
3. 图标现在是 128px 缩略图。若将来 UI 出现 >128 CSS px 的用法（全屏封面、
   整合包详情大图），需同步调大 `ICON_MAX_EDGE`。
4. 缓存文件会随用户实例数增长（每版本目录一条，约 200-400 B），已有自动淘汰兜底。
5. **升级前就存在的实例不会自动瘦身**：`instance.rs` 只在 `icon_data` 为 `None` 时
   才回填（`enrich_instance_icon` 同理），已写进 `instances.json` 的全尺寸 base64
   会一直被 `GET /api/instance` 返回、被每次 `save_to_file()` 重新序列化。
   即"22.4 MB 搬四次"对老用户依然成立，只有新安装/导入的记录会缩小。
   没有做迁移：批量重写 10MB 的 JSON 有写坏风险，而收益是一次性的。
  逃逸口：删掉对应实例的 `icon_data` 字段（或删 `instances.json` 让扫描重建）。
6. **图标指纹缓存的失效窗口**：`(长度, mtime)` 与扫描缓存同一套取舍。极端情况下
   （同长度改写 + 文件系统 mtime 粒度粗，如 FAT/exFAT 的 U 盘）进程内会一直读到旧图，
   重启进程即恢复。同样地，`metadata.modified()` 取不到时指纹退化成 `(长度, None)`。
7. **源图面积上限 4096×4096**（`MAX_SOURCE_PIXELS`）：超过的 PNG 不缩、保留原字节。
   这条首先是安全边界 —— 解码缓冲按 `宽 × 高 × 通道` 一次分配，30000×30000 的
   PNG bomb（文件本身几十 KB）要 3.6GB，而 Rust 分配失败是 abort 不是 panic，
   后端进程会直接消失；图标字节来自第三方整合包下载，不可信。
   回归覆盖：`util::pcl_icon::tests::png_bomb_dimensions_are_refused_before_allocating`。
