# ADR-089：下载中心按资源类型分组与折叠

| 属性 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-01 |
| 决策者 | AI Agent |

## 背景

issue #131：下载中心把整合包、模组、资源包、光影等任务平铺在同一张列表里，用户无法按资源类型分类回查历史下载（"模组和整合包/资源包会结合在一起，不便于分类"），并要求提供折叠功能。

现状约束（读码确认）：
1. `DownloadTask.type` 粒度太粗，只有 `game | resource | repair | file | batch | java | modpack`。模组、资源包、光影**全部**落成 `file` 或 `batch`，类型信息在发起点丢失。
2. 真正区分它们的 `category`（`mods` / `resourcepacks` / `shaderpacks` / `datapacks` / `saves`）只作为目录参数 POST 给 `/api/resource-download/start`，用于决定目标目录（`resource_download.rs` 的 `cat` 匹配），**后端任务快照不回传该值**，SSE 的 `resources` 通道也没有它。
3. `DownloadSpeedGraph` 每 500ms 采样、约 20s 窗口，**卸载即清空历史**（`下载中心 UI 规范`）。因此折叠不能条件渲染。
4. 任务数据整体持久化在 localStorage `qomicex-download-tasks`，所以**旧任务没有新字段**，分组逻辑必须能容忍缺字段。

## 决策

采用「前端新增可选字段 `resourceKind` + 集中分组工具 + `hidden` 视觉折叠」方案。

1. **数据模型**（`src/types/index.ts`）：新增 `DownloadResourceKind = 'mod' | 'modpack' | 'resourcepack' | 'shader' | 'datapack' | 'save'`；`DownloadTask` 增可选 `resourceKind?`。字段名刻意避开 `category`——后者在代码里专指后端目录路由字符串（含复数/大小写差异）。

2. **集中分组工具**（新建 `src/lib/downloadGroups.ts`）：
   - `normalizeResourceKind(raw)`：归一化大小写、复数、分隔符差异（`resource-pack`/`resource_pack`/`resourcepack` 等价；`shaderpack(s)`→`shader`；`mods`→`mod`；`saves`→`save`）。**认不出返回 `undefined`，绝不兜底成 `mod`**。
   - `getTaskGroup(task)`：`resourceKind` 优先 → 按 `type` 回退（`modpack`→整合包，`game`/`repair`→游戏，`java`→Java）→ 其余（`file`/`batch`/`resource` 及旧数据）归「其他」。
   - `DOWNLOAD_GROUP_ORDER`：固定顺序 game → modpack → mod → resourcepack → shader → datapack → save → java → other。
   - `groupTasks(tasks)`：固定顺序输出**非空**分组，组内保持 store 顺序（新任务在前）。
   - `readCollapsedGroups` / `writeCollapsedGroups`：独立 localStorage 键 `qomicex-download-groups-collapsed`，与任务数据隔离。解析失败 / 非数组 / 含非法键 → 回退为空集合（全部展开）。

3. **发起点写入分类**（旧任务不迁移）：
   - `lib/quickInstall.ts`：批次父任务写 `normalizeResourceKind(main.category)`——**按主资源归类**，一个 batch 可能「本体是模组、依赖里有光影」，用户界面看到的是本体，按依赖分类与直觉相反。
   - `lib/updateMods.ts`：两处 `addTask`（含启动失败任务）写 `'mod'`。
   - `pages/ResourceDetail.tsx`：资源下载写 `normalizeResourceKind(category)`；FTB JSON 导出写 `'modpack'`（描述整合包内容）。
   - `plugins/plugin-api.ts`：`opts.category` 归一化后写入任务。**不能把字段塞进 `opts`**——插件桥用 `JSON.stringify(opts)` 把整个对象发给后端。
   - 其余发起点（`type:'modpack'` 的整合包对话框、`ToolboxTab` 任意 URL、`Settings` 的 java、`Instances` 的 game/repair）保持不变，靠 `type` 回退分组。

4. **分组与折叠 UI**（`src/pages/DownloadCenter.tsx`）：
   - 在既有状态 Tabs 过滤（`filtered`）**之后**用 `useMemo` 分组；顶部任务数与空状态沿用过滤后结果。
   - 卡片渲染抽为**模块级**组件 `TaskCard`：若定义在组件体内，每次渲染产生新组件身份，React 会卸载重挂整棵子树 → 速度图历史被清空。
   - 分组头用原生 `button` + `aria-expanded` + `aria-controls`；`ChevronDown` 配 `transition-transform`，折叠时 `-rotate-90`。
   - 折叠**用 `hidden` 属性做视觉隐藏，卡片保持挂载**，速度图采样历史与 SSE 更新对账都不中断。
   - 折叠动画走新增的 `.anim-transition` 工具类：`[data-anim-enabled="false"]` 与 `prefers-reduced-motion: reduce` 下 `transition: none`（Tailwind 的 `transition-*` 不读 `--anim-duration-multiplier`，必须在 CSS 兜住）。

5. **i18n**：在 `qomicex-tauri-i18n` submodule 的 7 个语言文件 `downloads.ts` 新增 `groups.{game,modpack,mod,resourcepack,shader,datapack,save,java,other,inProgress}`，schema 由 zh-CN 自动派生。

**关键健壮性修复（实测发现）**：`normalizeResourceKind` 必须先做 `typeof raw !== 'string'` 守卫，不能只靠 TS 签名。任务来自 localStorage 与插件调用方，运行期可能是任意 JSON；传入对象时 `raw.trim is not a function` 会让 `useMemo` 抛异常 → **下载中心整页被 ErrorBoundary 兜成白屏**（实测复现并已修复）。

**关键健壮性修复 2（评审发现，v1.1）**：`readCollapsedGroups` 曾用 `parsed.filter(isDownloadGroupKey)` **部分接受**脏数组 —— `["mod","__proto__"]` 会返回 `["mod"]`，模组分组仍保持折叠。这直接违反本决策第 2 条与《下载中心 UI 规范》写明的「含非法键一律回退为全部展开」契约（即**代码没有实现自己声明的规格**）。改为「全有或全无」校验：`if (!parsed.every(isDownloadGroupKey)) return []`。Sourcery 与 CodeRabbit 各自独立报出同一条，指向同一处。
> 复盘：首轮浏览器实测其实抓到了该行为（`["mod","NOPE","__proto__",123,null]` → `collapsed:["mod"]`），但被误判为「脏数据边界全部正确」。**测试输出正确而判读错误**，是本次流程的真实教训 —— 边界用例的断言必须显式写成期望值再比对，不能靠肉眼扫结果。

**舍弃方案**：
- *后端任务快照返回 category*：需改 `TaskSnapshot` + SSE + 前端类型 + API 契约与文档；而 issue 诉求纯属前端呈现，收益不抵契约风险。若将来需要「插件/外部发起的任务也自动分类」，可再评估。
- *只按现有 `type` 推断*：`file`/`batch` 无法再细分，模组与光影仍混在一起，实际不解决 issue。
- *折叠用条件渲染*：卸载会清空 `DownloadSpeedGraph` 速度历史，违反下载中心 UI 规范。
- *折叠状态写进 `downloadStore` 任务数据*：用户偏好不属于任务数据，且会与任务持久化耦合。
- *分类缺失时默认归 `mod`*：会把光影/资源包误报成模组。

## 备选方案

### 方案 后端任务快照返回 category
- 优点：插件/外部发起的任务也能自动分类；分类是权威值
- 缺点：改动 TaskSnapshot + SSE + 前端类型 + API 契约与文档；issue 诉求纯属前端呈现
- 为何不选：契约变更风险大于收益，且后端 category 语义是目录路由（含复数），与展示分类不完全等价

### 方案 只按现有 type 推断分组
- 优点：零改动，最小
- 缺点：file/batch 无法再细分，模组与光影仍混在一起
- 为何不选：不解决 issue 的核心诉求

### 方案 折叠用条件渲染
- 优点：实现更简单
- 缺点：卸载清空 DownloadSpeedGraph 速度历史，违反下载中心 UI 规范
- 为何不选：保留卡片挂载是硬约束

### 方案 折叠状态写入 downloadStore 任务数据
- 优点：无需新 localStorage 键
- 缺点：用户偏好与任务数据耦合；任务被清空时折叠偏好一并丢失
- 为何不选：独立键隔离更干净
