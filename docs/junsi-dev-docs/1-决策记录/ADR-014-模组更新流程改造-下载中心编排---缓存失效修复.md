# ADR-014：模组更新流程改造：下载中心编排 + 缓存失效修复

| 属性 | 内容 |
|:---|:---|
| 状态 | 已采纳 |
| 日期 | 2026-08-15 |
| 决策者 | AI Agent |

## 背景

模组更新原走后端同步端点 batch_update_mods（服务端直接下载替换），完全绕过下载中心；且 ModUpdateDialog.onDone 与 ModCard.onRefresh 只调 loadMods() 未 cacheInvalidate，命中 30s 新鲜缓存导致更新后列表不刷新；更新完成后 Toast 时机不可控；ModCard 蓝点无版本提示。

## 决策

前端编排方案（方案A）：新建 src/lib/updateMods.ts，每个更新 startResourceDownload → addTask 进下载中心 → 轮询 getResourceDownloadProgress → completed 后 deleteMod 删旧文件 → 全部完成才 Toast。统一 refreshModsAfterUpdate 做 cacheInvalidate。三个入口（ModUpdateDialog 批量、工具栏批量、ModCard 单卡）均改走新 helper，ModCard 新增 onUpdated 移除更新标记。蓝点移出 h3 外包 Tooltip 显示「可更新至 X」。后端 batch_update_mods 保留未用。

## 备选方案


### 方案 方案B 后端异步批次
- 优点：下载管理集中在后端
- 缺点：后端+前端双改，改动面大，需改 batch_update_mods 契约
- 为何不选：未选：改动更大且方案A已完全复用现有 downloadTo/start/delete 端点

### 方案 仅修 cacheInvalidate
- 优点：极小改动
- 缺点：不满足任务进下载列表与 toast 时机两项需求
- 为何不选：未选：需求覆盖不全

## 影响
- 前端 4 个文件（updateMods.ts 新增，ModUpdateDialog/ModCard/InstanceDetail 修改）
- 后端无改动，batch_update_mods 端点保留
- 下载中心出现更新任务并实时显示进度
- 更新列表刷新与蓝点标记移除即时生效
