## 背景

上游 C:\Project\world-viewer 在 8828130 之后新增两个提交，本项目（移植到 b2c2c0e）均未包含：

1. 4e6f71d feat(render): 生物群系染色与水面透视渲染
   - 原先草/叶一律乘固定平原绿，无群系差异；水面是单色平面，看不到水底。
   - 新增 biome.rs + biome_tints.rs（1.7-1.17 数字 id 表 79 条 + 1.18+ 命名空间表 67 条），
     按真实 biome 查 grass/foliage/water/dry-foliage 四类色板。
   - 列扫描升级为 ChunkData::scan_column：遇水面继续下钻记录海底，按深度混合水色与水底色。
   - 新增 RenderOpts（water/shading/altitude）与瓦片 URL 查询参数，前端加开关。

2. 1dc33cf perf(tiles): 瓦片渲染缓存与并发优化（实测视口渲染 332ms -> 164ms，2.0x）
   - region：缓存 region 文件句柄与 8KB header，改用位置读（pread）使句柄可跨线程共享。
     原先每个 chunk 都重开文件并重读 header，一个 z=0 瓦片要 open 324 次。
   - render：TileCache 淘汰由「随机踢 25%」改为 LRU，并修掉 O(n^2) 的逐条最小值扫描。
   - render：chunk 以 Arc<ChunkData> 交出，锁只保护 map，几十毫秒的 surface 扫描移出锁。
   - 容量 4096 -> 8192：根因是容量而非淘汰策略，一个 z=0 视口需约 6500 个 chunk。
   - 前端 bitmap 缓存加上限 512，此前无上限（约 256 MB）。

本项目的额外适配点：WorldViewService.tile() 把**整个 session 锁**跨 render_tile 持有，
比上游的 cache 锁更粗，串行化问题同样存在（上游实测 6 并发仅 0.94x）。移植时一并收窄。

## 决策

采用「适配新架构」全量移植，分两个 commit 保留上游语义：

1. 路径 crate:: → super::；上游独立 tests/*.rs 并入 ported_tests.rs 的 mod（后端是 bin crate，无 lib target）。
2. 保留本项目在 ADR-080 修的 ChunkKey = (dim, cx, cz)（上游是二元组），逐处适配而非整文件替换。
3. 染色分派（关键契约）：调色板颜色是灰的（max-min <= 24）→ 原版公式 (base*tint)>>8；
   已是彩色（水 #2e43f4、芦苇、模组树叶）→ 相对平原基准的比例缩放。若对已着色方块也乘 tint，
   会被二次压暗（水变近黑）。这是 ADR-001 之外新增的一条契约。
4. 锁收窄：WorldSession.cache 改 Arc<TileCache>；tile()/probe_block() 只在取 region_dir/ymax
   那一段持锁，几十毫秒的渲染在锁外。TileCache 内部用 Mutex 只保护 map，acquire() 交出 Arc。
5. 前端：RenderFlags 写进瓦片 URL（CachedTileLayer 的模板比较自动清缓存重绘，无需额外失效逻辑）；
   CachedTileLayer 加 maxCached=512 的 LRU（Map 插入顺序即使用顺序，淘汰取第一个 key）。
6. i18n：qomicex-tauri-i18n submodule 补 render/waterToggle/shadingToggle/altitudeToggle 四键 × 7 语言。

跳过项：上游 5 个 perf_*.rs 测试并入 ported_tests.rs 的 mod；scripts/*.mjs（Playwright CDP 探针）
不搬运（本项目无 playwright 依赖）。

上游未采纳项：无，两个提交的功能与修复全部同步。

## 备选方案

### 方案 拆分两次移植（先功能后性能）
- 优点：未说明
- 缺点：两个提交都改 render.rs / region.rs，第二次要重改同一批代码，冲突成本高于合并
- 为何不选：不选：改动面重叠

### 方案 只移植功能或只移植性能
- 优点：未说明
- 缺点：功能（用户可见）或性能（最痛的串行化）会延后
- 为何不选：不选：两项都对应明确需求

### 方案 全量移植（采纳）
- 优点：一次同步到位；分两个 commit 保留上游语义，便于回溯
- 缺点：单次 PR 较大（后端约 1900 行 + 前端 + i18n）
- 为何不选：采纳：改动重叠，合并移植反而冲突更少
