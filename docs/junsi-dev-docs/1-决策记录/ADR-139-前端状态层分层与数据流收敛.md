# ADR-139：前端状态层分层与数据流收敛

| 属性 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-11-21 |
| 决策者 | AI Agent |
| 关联 | ADR-089（下载中心分组）、ADR-095（会话级共享状态）、ADR-118（受限文件待补全）、ADR-134（待补全不降级失败）、ADR-138（任务卡去重） |

## 背景

前端状态层此前有四种写法并存，且没有「谁持有服务端数据」的约定：

- zustand：`favoritesStore` / `pluginStore` / `updaterStore`，用 selector 订阅。
- 手写 pub-sub：`downloadStore` / `javaStore` / `pendingFavoriteInstallStore`（`getX` + `subscribe`），消费者各自 `subscribe(() => setState([...getX()]))`（`DownloadCenter`、`TaskCompletionNotifier`、`Settings`、`InstanceDetail` 各写一遍）。
- React Context：`RunningContext`（411 行，启动编排 + 轮询 + 资源遥测 + 崩溃弹窗 + 通知桥）、`MessageBox`、`I18n`、`closeGuard`。
- 模块级缓存：`api/settings.ts` 的 `cached + listeners`、`lib/simple-cache.ts` 的字符串前缀失效。

实测缺陷（非推测）：

1. `RunningContext` 的 provider value 是**内联对象字面量**（`RunningContext.tsx` 的 `return`），每次资源遥测 tick（1s）都换引用，`Sidebar` / `Instances` / `InstanceDetail` / `RunningInstances` 全部重渲染；`Sidebar` 只用到 `runningInstances.length > 0`。同一分支还会每 5s 重启一条资源轮询链，旧链无人回收。
2. 服务端实体没有归属：`getInstances()` 有 6 处调用方、`getAccounts()` 有 5 处，各自请求、各自缓存；实例对象的缓存键靠 `cacheInvalidate('api-instance-')` / `cacheInvalidate('api-')` 前缀失效，会误伤无关缓存，且跨页写入后读方看不到变更。
3. settings 有 3 条读取路径：`api/settings.ts` 缓存、`Settings.tsx` 自己的 state、6 处组件 `await loadSettings()`；并发调用不合并，冷启动会同时打多轮 `/settings`。
4. 全局进度流只属于下载中心页：`useDownloadSSE` 仅在 `DownloadCenter` 挂载，离开 `/downloads` 流即断开，任务进度冻结、完成通知不触发。

参考仓库 `qnxg/weihuda_weapp_tsumiki` 的 Context-Hook 方案（Context 只存原始状态 + setter，业务在 hook）是针对 Taro 无法加载 zustand bundle 的限制。本项目已安装并使用 zustand，不引入该限制。

## 决策

1. **分层**：`api/` 只做 HTTP 与错误映射；`lib/` 放纯逻辑（无 React、无 store）；`stores/` 持有跨组件状态；`contexts/` 只放「必须随组件树生命周期存在」的状态与动作（当前仅启动编排与 UI 基础能力）；`hooks/` 做组合与副作用。
2. **全局状态统一 zustand + selector**。不再新增手写 pub-sub store，也不再新增承载服务端数据的 Context。既有手写 store 保留 `getX/subscribe` 作为命令式接口，但**渲染读取必须走导出的 hook**（`useDownloadTasks`、`useJavaRuntimes`），禁止在组件里手写 `subscribe + setState`。
3. **服务端实体由 store 唯一持有**：`instancesStore`（列表 + 默认实例）、`accountsStore`（列表 + 默认账户）。读方只用 `load/loadX(force)/selector`，页面与对话框**不再直连** `getInstances()` / `getAccounts()`。
4. **写入用变更广播，不做整表重拉**：`api/` 的写操作成功后 `emit` 一个 `entityPatch` 变更（upsert / remove / default / reload）；store 就地打补丁。无法从返回值推导的变更（备份导入）才用 `reload`。
5. **并发与陈旧保护**：`refresh()` 共享 in-flight 请求；请求期间若有更权威的写入（`syncScan` 的 `replace` 或 CRUD 补丁），旧快照按版本号丢弃，只采纳默认项。`loadSettings()` 同样合并并发调用。
6. **订阅粒度**：高频数据（进程 CPU/内存）不进低频列表；`runningStore` 用 `useRunningInstances` / `useHasRunningInstances` / `useInstanceResourceUsage` 分别订阅。Context 的 value 必须 `useMemo`，且把**动作**与**状态**拆成两个 Context（`useRunningActions` / `useRunningState`），动作订阅者不随状态 tick 重渲染。
7. **全局事件流所有权在 App**：`/progress/stream` 由 `startProgressSync()` 在 `ProgressStreamBridge` 中唯一订阅，`downloadStore` 是进度的唯一真相；页面只读 store。SSE 对账的竞态判定（`retryPending` 跳过、缺项限次回查、已清除任务不补卡）原样保留在 `lib/progressSync.ts`。

## 备选方案

### 全量照搬参考仓库的 Context-Hook
- 优点：与参考实现一致，Context 极简、业务在 hook
- 缺点：需重写 6 个既有 zustand store；本项目没有 Taro 的 bundle 限制；Context 无法按字段选择订阅，天然带来本次要修的整树重渲染
- 为何不选：收益为负

### 引入 TanStack Query 统一服务端缓存
- 优点：请求去重、失效、重试、缓存策略开箱即用
- 缺点：新增运行时依赖与一套新的心智模型；本项目服务端是本地 axum（毫秒级），真正的痛点是写入后的跨页可见性，而事件广播已足够
- 为何不选：依赖换不来对应的复杂度

### 保持多种写法并存，只修单点 bug
- 优点：改动最小
- 缺点：新增状态时仍会随机选一种；`subscribe + setState` 的重复样板会继续复制
- 为何不选：本次问题正是缺约定导致的

## 影响

- 新增：`stores/{runningStore,instancesStore,accountsStore}.ts`、`lib/{entityEvents,entityPatch,progressSync,downloadStatus}.ts`、`components/ProgressStreamBridge.tsx`。
- 删除：`hooks/useDownloadSSE.ts`（流所有权上移）；`DownloadCenter` 中 345 行对账逻辑与 dismissed 存储。
- 语义变化：任务进度在离开下载页后继续推进（修复）；实例/账户的跨页一致性来自变更广播；资源遥测不再触发整树重渲染。
- 验证：`pnpm run typecheck`、`pnpm run lint`、`pnpm run test:entity-stores`、`pnpm run build`；手工：游戏中侧边栏无每秒重绘、离开 `/downloads` 后进度继续、设置页改动跨页即时生效。
