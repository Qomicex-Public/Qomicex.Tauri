# ADR-085 启动器更新检测改为通道（train）模型：跨通道不降级、开发版不提示

- 状态：已接受
- 日期：2026-09-21
- 影响面：启动器本地后端（`endpoints/update.rs` + 新增 `services/update_channel.rs`）、
  前端（`App.tsx` / `Settings.tsx` / `UpdateDialog.tsx` / `api/update.ts` / 新增 `lib/updateChannel.ts`）、
  Web.Backend（`utils/version.ts` / `utils/client-license.ts` / `routes/client/{update-plan,version}.ts`）、
  i18n submodule（7 语言）

## 背景与三个症状

用户报告：

1. **正式版无法更新到 beta** —— 在设置里选 beta 通道，检查更新恒提示"已是最新版本"。
2. **beta 持续提示更新到正式版** —— beta 构建每次启动都弹"发现新版本 0.1.0-release1.0"，
   照做即从 beta31 退回 release1.0。
3. **开发版也提示需更新到正式版** —— 本地构建（版本号 `0.1.0`，无通道后缀）同样被推 release。

线上实测（2026-09-21）：

| 请求 `/api/client/update/plan` | 返回 | 症状 |
|---|---|---|
| `current=0.1.0-beta23.0&channel=beta` | 200 → `0.1.0-release1.0` | ② |
| `current=0.1.0-release1.0&channel=beta` | 204（beta31 已存在却拿不到） | ① |
| `current=0.1.0`（无后缀） | 200 → `0.1.0-release1.0` | ③ |

GitHub Releases 实况：`v0.1.0-beta31.0` 发布于 09/21，`v0.1.0-release1.0` 发布于 09/13
—— **beta31 比 release1.0 更新**。

## 根因（4 处，横跨两个仓库）

1. **Web.Backend `api/src/utils/version.ts`**：`TYPE_ORDER = { alpha:0, beta:1, release:2 }`，
   `compareVersions` 把 release 一律排在 beta/alpha 之上。
2. **Web.Backend `api/src/utils/client-license.ts`**：`getAllowedTypes('beta') = ['beta','release']`。
   与 ① 叠加：beta 通道的候选池里 release 永远最大 → `latest` 恒为 release
   → beta 用户既选不到 beta 版本，又被判"该更新到 release"（降级）。
3. **前端 `App.tsx` / `Settings.tsx`**：`localStorage.getItem('update-channel') || 'stable'`
   —— 默认通道硬编码 `stable`，**与已安装构建所属通道无关**。
   beta/alpha/开发构建一律按 stable 请求，于是都被推去 release。
4. **本地后端 `endpoints/update.rs`**：`plan()` 把上游返回**原样透传**，本地零校验；
   且未转发 `Authorization: Bearer <machineCode>`，上游的灰度门控（weight + machineHash）
   与许可证通道钉住实际失效。

> 注：症状 ③ 的 `0.1.0` 能命中，是因为 `parseVersion` 的 `SIMPLE_RE` 把裸 `X.Y.Z`
> 归为 `type: 'release', suffix1: 0`，于是任何 `-releaseN.0`（N>0）都"更新"。

## 决策：通道 = 独立的发布列车（train）

参照 Chrome / VSCode / Firefox / Windows Insider 的通道模型：

1. **每条通道是独立的发布列车**。发布版本只属于一条列车：
   `release`(稳定) / `beta` / `alpha`。列车按"新鲜度"排序 `release < beta < alpha`，
   但**低新鲜度列车的版本不一定更旧**。
2. **各列车序数独立计数**，跨列车比序数没有意义：
   `0.1.0-beta31.0` 与 `0.1.0-release1.0` 的 31 vs 1 不可比。
3. **客户端只订阅一条列车**，仅当**同列车内**出现更新时才提示
   （同列车内按 `major.minor.patch + 序数` 数值比较，`beta10.0 > beta9.0`）。
4. **永不跨列车自动更新**。切换列车是用户显式动作（设置里的通道选择器）；
   跨列车时以**发布时间**判新鲜度——目标发布晚于当前构建才允许，
   且 UI 必须标注为"切换通道"而非普通版本升级。
   反向（beta31 → release1.0）一律拒绝，这是降级。
5. **开发构建**（裸 `X.Y.Z`，无 pre-release 后缀）不属于任何已发布列车
   → 不接收任何更新提示，设置页显示"开发构建，不检查更新"。
6. **`required`（强制更新）**在列车内优先；可跨列车但需明确标注。
7. **灰度门控（weight）继续留在服务端**，客户端不参与决策。

## 实现要点

### Web.Backend

- `utils/version.ts`：新增 `trainOf(version)` 与
  `isUpdateFor(current, latest, currentCreatedAt, latestCreatedAt)`。
  同列车 → `compareVersions` 数值比较；跨列车 → 比较 `versions.createdAt`，
  `current` 不在表中（开发构建）→ 一律 false。
  `compareVersions` 保持原语义，仅用于**同列车内**排序。
- `utils/client-license.ts`：`getAllowedTypes('beta')` 由 `['beta','release']` 收窄为 `['beta']`。
  `null`（旧版启动器未传）保持 `['beta','release']` 不变，避免影响存量客户端。
- `routes/client/update-plan.ts` 与 `routes/client/version.ts`：用 `isUpdateFor` 取代 `isNewer`；
  响应新增 `channel`（候选所属列车）与 `channelSwitch`（布尔，跨列车时为 true）。

### 启动器本地后端

- **新增 `services/update_channel.rs`**（无新依赖，后端未引 `semver`）：
  `Train{Release,Beta,Alpha,Dev,Unknown}`、`train_of()`、`parse_train_version()`、
  `is_train_upgrade()`、`normalize_channel()`（`stable`→`release`）、`effective_channel()`。
  8 个单元测试覆盖全矩阵。
- `endpoints/update.rs`：
  - `plan()` 有效通道 = 显式 query > 已安装构建推导的列车；推导为 dev/unknown 时
    直接返回 `hasUpdate=false` + `reason:"dev-build"`，**不发上游请求**。
  - 上游请求带 `Authorization: Bearer <machineCode>`（`license_core::machine_code()`，
    无 feature gate），恢复灰度门控与许可证通道钉住。
  - **本地不变量守卫** `guard_train_plan()`：候选解析失败 / 候选列车 ≠ 请求通道 /
    同列车且候选 ≤ 当前 → 一律 `hasUpdate=false` 并 `tracing::warn!` 留痕。
  - `check()` 同样转发 channel + machineCode 并过同样的守卫（修掉它原本完全忽略 channel 的问题）。
  - 响应新增 `channel` / `channelSwitch` / `reason`。

### 启动器前端

- **新增 `src/lib/updateChannel.ts`**：唯一版本→列车解析源
  （`trainOf` / `isDevBuild` / `resolveChannel` / `trainLabelKey` / `UPDATE_CHANNEL_KEY`）。
  `resolveChannel()` = localStorage 显式选择 > 已安装构建推导；dev/unknown → `undefined`。
- `api/update.ts`：`UpdatePlan` 增加 `channel` / `channelSwitch` / `reason`；
  删除 `checkRequired`（`plan.required` 已由上游提供，省掉一次往返）。
- `App.tsx`：用 `resolveChannel()`；`required = plan.required === true`；
  snooze 键由 `version` 改为 `channel:version`（避免跨通道复用同一 snooze）；dev 构建跳过检查。
- `Settings.tsx`：通道选择器默认值改为 `resolveChannel()`（不再硬编码 `stable`）；
  版本徽章改用 `trainOf()`（修复 alpha 显示"测试版"、开发构建显示"稳定版"）；
  dev 构建显示"开发构建，不检查更新"；alpha 选项去掉硬编码 `'Alpha'` 字符串改用 i18n。
- `UpdateDialog.tsx`：`channelSwitch=true` 时标题改为"切换到 {channel} 通道"，
  并加通道切换说明条，避免用户误以为是普通升级。
- `api/announcements.ts`：`resolveChannel()` 改复用 `lib/updateChannel.ts`，
  消掉一套重复且同样错误的解析（它曾把正式版 `-release5.0` 之外的带 `-` 版本都算 beta）。

### 清理

删除 `src-tauri/src/version_order.rs` 与 `src-tauri/tests/version_order.rs` 及
`lib.rs` 的 `pub mod version_order;`。该模块的 `is_update_available` **全仓库无调用方**
（仅其自身测试与一个集成测试引用），是已被绕过的死代码；其"数值感知比较"职责由
`services/update_channel.rs` + 单元测试取代，且新增了跨列车防护。

   但 `deploy.yml` 的 `Cloudflare API Authentication failed (status: 400) [code: 9106]`

## 2026-10-01 补充（v1.1）：弹窗通道名本地化 + `trainOf` 与后端语义对齐

ADR-085 落地后遗留两处问题，本次一并修掉。

### 1. 更新弹窗把后端原始通道 key 直接插进文案

`UpdateDialog.tsx` 的 `channelSwitchTitle` / `channelSwitchNotice` 直接用 `plan.channel`
填充 `{channel}`，中文句子里显示成 "beta" / "release"；而设置页「关于」徽章
（`Settings.tsx` 的 `trainLabelKey(installedTrain)`）与 #130 引入的
`UpdateCompleteDialog`（`trainLabelKey(trainOf(version))`）都用本地化标签
（稳定版 / 测试版 / 开发版）。同一信息三处口径不一致。

**修法**：`lib/updateChannel.ts` 新增 `channelLabelKey(channel)` —— 按后端
`Train::as_str()` 口径（`release` | `beta` | `alpha` | `dev`）映射到
`trainLabelKey()` 的 i18n key；无法识别时返回 `undefined`，由调用方回落原始字符串
（不猜）。弹窗与徽章自此共用同一套标签，**未新增 i18n key**（复用
`settings.about.*`），不涉及 i18n submodule。

不直接改用 `trainOf(plan.version)` 的原因：`plan.channel` 是后端已经裁决好的目标
通道，直接映射无需再从版本串二次推导，避免两套判定再次漂移。

### 2. `trainOf` 与后端 `train_of` / `parse_train_version` 语义漂移

实测行为对照：

| 输入 | 后端 | 修复前前端 | 修复后前端 |
|---|---|---|---|
| `''`、`'v'`、`'vv'` | Unknown | **dev**（关于页徽章「开发构建」，`devBuild=true`） | unknown（「未知构建」） |
| `1.0.x`（核心段含非数字） | Unknown | **dev** | unknown |
| `vv1.0.0-beta1.0`（连续 `v` 前缀） | beta | unknown（只剥一个 `v`） | beta |
| `0.1.0` / `0.1.0-beta31.0` / `0.1.0-release1.0` | 各自 train | 不变 | 不变 |

第 3 行是用户可见的行为修复：连续 `v` 前缀的真实构建此前被判 `unknown`，
`resolveChannel()` 返回 `undefined` → `App.tsx` 后台检查与 `Settings.tsx` 手动检查都
静默返回「已是最新」。修复后按 beta 正常检查。

第 1、2 行只影响展示与 `devBuild` 门控：`resolveChannel()` 与
`announcements.ts::resolveChannel()` 对 `dev` 与 `unknown` **都**返回 `undefined`，
因此更新检查与公告过滤行为不变；但把「未知」显示成「开发构建」本身就是错误信息，
与后端解析结果矛盾。

**修法**：`trainOf` 改为 —— `v+` 全剥（对齐后端 `strip_v` =
`trim_start_matches('v')`）、空串直接 `unknown`、核心段必须全数字且至少有一段非空
（对齐后端 `core_is_numeric` + `nums.next()?`）。

### 回归防护（勿改动）

- `TYPE_SEGMENT_RE = /^(alpha|beta|release)(?:\d|$)/i` **不能带前导 `-`**：调用方
  喂进来的是已 `slice(dash + 1)` 去掉 `-` 的串，带 `-` 会恒不匹配——历史实现
  （`/-(alpha|beta|release)(\d+)/i`）正是如此，导致 release/beta/alpha 全部落入
  `unknown`，进而 `resolveChannel()` 返回 `undefined`、更新检查静默失效。代码内已留注释。
- `/i` 不能去掉：后端先 `to_ascii_lowercase`，`Beta1` / `ALPHA1` 同样要被识别
  （`m[1].toLowerCase()` 依赖该 flag）。
