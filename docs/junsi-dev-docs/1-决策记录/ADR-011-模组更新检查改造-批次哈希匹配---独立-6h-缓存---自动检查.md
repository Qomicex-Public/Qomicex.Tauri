# ADR-011：模组更新检查改造：批次哈希匹配 + 独立 6h 缓存 + 自动检查

| 属性 | 内容 |
|:---|:---|
| 状态 | 已采纳 |
| 日期 | 2026-08-15 |
| 决策者 | AI Agent |

## 背景

原 check_mod_updates（instance_files.rs）逐 Mod 拉版本列表（Modrinth 无 loader/gameVersion 过滤、CF pageSize=1），仅按 version_compare 字符串比较判定更新，不经任何缓存，且依赖 enrich 反查出的 id。问题：慢（N 次串行网络请求）、判定不严谨（无发布时间/哈希比对）、每次打开检查更新对话框都全量联网。

需求：本地模组列表加载后自动检查更新。批次哈希匹配：Modrinth 严格两步（POST /v2/version_files 用 SHA1 反查当前版本 → POST /v2/version_files/update 传 loaders+game_versions 反查最新版本）；CurseForge POST /v1/fingerprints 指纹反查 exactMatches（file + latestFiles）。判定规则：updateFile.Available 为真 && 新版本发布时间晚于本地文件 && 新版本文件哈希 ≠ 本地文件哈希。新建立独立 6h 缓存门控（缓存新鲜不联网），保留"检查更新"按钮 + ModUpdateDialog 作强制刷新。

## 决策

1. 核心库（qomicex-core-rust）新增两个方法：ModrinthSource::get_latest_versions_from_hashes（POST v2/version_files/update，body {hashes, algorithm:"sha1", loaders, game_versions}，响应 哈希→VersionInfo 映射）；CurseForgeSource::get_fingerprint_matches（POST /v1/fingerprints，解析 exactMatches 的 file + latestFiles 到 CurseForgeFingerprintMatch，键取 file.fileFingerprint ?? file.id）。
2. 后端 check_mod_updates 重写为批次实现（refresh_mod_updates）：get_mod_list_light 轻量扫描（自带 sha1_hash + cf_hash）→ Modrinth 两步批量（tokio::join!）→ CF 指纹批量；判定严格按 Available + 发布时间晚于本地 + 哈希不同。项目 id 取反查结果（cur.project_id / cur.mod_id），不再依赖 enrich。
3. 独立 update 缓存：{data_dir}/QML/mods-update-cache/{id}-updates.json，6h TTL（UPDATE_CACHE_TTL_SECS）。check-updates 新增 force 查询参数：force=1 强制联网；force=0 缓存命中直接返回 refreshed=false。
4. 新增 GET /instance/{id}/files/mods/update-cache（只读缓存 + stale 标志）。前端列表加载后自动检查：先读 update-cache 标记已缓存的更新；仅 stale 时弹"正在检查模组更新…" Toast 并调用 check-updates，完成后有更新弹"发现 N 个模组可更新"。手动按钮/对话框走 force=true。
5. 移除旧版 per-mod 检查 helper（check_modrinth_update/check_curseforge_update/version_compare/version_parse/urlencode）。

## 备选方案


### 方案 后端继续用原始 reqwest 逐 Mod 拉版本列表
- 优点：改动小，不动核心库
- 缺点：仍是 N 次串行请求、无 loader/gameVersion 过滤、无法批次；判定依旧粗糙
- 为何不选：决策 #1 采用批次方案，复用并扩展核心库批量反查能力

### 方案 复用现有 mods-cache 存更新结果
- 优点：少一个缓存文件
- 缺点：mods-cache 由 metadata/enrich 使用，语义耦合；update 结果结构不同
- 为何不选：决策 #3 独立 mods-update-cache，避免互相污染

### 方案 check-updates 单端点返回 {updates, refreshed}，前端总是调用
- 优点：少一个端点
- 缺点：前端无法在联网前弹 Toast（refreshed 事后才知道）
- 为何不选：决策 #4 增加 update-cache 廉价端点，实现『开始获取时弹 Toast』

## 影响
- qomicex-core-rust：ModrinthSource trait + ModrinthBase 实现 + VersionFilesUpdateRequest 模型；CurseForgeSource trait + CurseForgeBase 实现 + CurseForgeFingerprintFile/Match/Hash 模型
- src-backend instance_files.rs：check_mod_updates 重写为 refresh_mod_updates，新增 mods_update_cache 端点与 update 缓存助手，路由新增 update-cache
- src/pages/InstanceDetail.tsx ModsTab：useMessageBox notify + 列表加载后自动检查 effect
- src/api/instance-files.ts：checkModUpdates 增加 force 参数、新增 getModUpdatesCache
- src/components/ModUpdateDialog.tsx：checkModUpdates 传 force=true
- 行为变更：不再依赖 enrich 的 modrinth_id/curse_forge_id（改用哈希直接匹配），可更新判定更严格（发布时间+哈希）
