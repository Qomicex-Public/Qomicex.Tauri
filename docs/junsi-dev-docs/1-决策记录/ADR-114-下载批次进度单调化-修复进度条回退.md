# ADR-114：下载批次进度单调化，修复进度条回退

| 属性 | 内容 |

| 日期 | 2026-10-16 |

## 背景

用户反馈安装实例时进度条反复横跳：模组文件「下载到 200/300 又跳回 100/300」、「眼看都到 99% 了又直接跳回 60%」。同类反馈还包括下载速度长期卡在数百 KB/s。

经代码定位，**进度回退有两处彼此独立的成因**，缺任一修复仍会回退：

1. **分子被清零** —— 下载器流式路径每次重试前执行 `ctx.stats.downloaded.store(0)`
   （`qomicex-downloader-rust/src/engine.rs::run_streamed`），把已下载计数打回 0；
   而 `download_batch` 的事件处理无条件执行 `e.0 = downloaded`，于是单文件进度
   直接归零（「200/300 跳回 100/300」）。

2. **分母持续增长** —— `download_batch` 的 `prog` 只包含**已发过首个 Progress 事件**
   的任务；排队中的任务随调度推进才以 `(0, total)` 进入 `prog`。因此分母 `Σtot`
   在批次前期不断变大，而分子（已完成字节）不动，百分比被摊薄（「99% 跳回 60%」）。

排查过程中的两个假设已被实测证伪，记录以免后人重走：

- **证伪 A（HTTP/2 多路复用）**：曾判断「小文件流式路径走 H2 多路复用」是慢的根因。
  关闭 Clash TUN 后直连实测：16 个真实 forgecdn 小文件并发 16 时，默认 H2 4.08MB/s
  vs 强制 H1 并行 1.95MB/s（H1 反而慢一倍）；预热 host 缓存强制走流式路径后
  H2 8.79 vs H1 6.17MB/s。H1 无收益且有害，假设作废。
  **教训：此前所有实测都经过 Clash TUN 全局代理，数据不可用于定论。**
- **证伪 B（assets 串行下载）**：曾以为实例安装的 assets 走 `qomicex-core-rust` 的
  `completer.rs::process_asset_index` 串行循环。调用链核查后：前端实例安装走
  `POST /instance/{id}/install`（`src/api/instance.ts:129`）→ `run_install_pipeline`
  → `get_miss_files_from_json` → `download_batch`（**已是并发**）；用户日志中 assets
  的 `.part` / `探测完成` / `已缓存` 三类标记可证。`process_asset_index` 只被
  `/versions/{name}/install` 与 `/resources/complete` 调用，不是实例安装路径。

**下载速度问题未在本次修复范围内**：本地实测 `download_batch` 并发 32/64 可达约
2MB/s，官方 assets host 单文件端到端约 0.9–3.1s；慢的真实归因（校园网出口整形 /
CDN 侧限速）未在本次定位完成，需真机慢网络复测。

## 决策

在 `src-backend/qomicex-backend/src/services/install_service.rs::download_batch`
做两处最小改动，使**同一批次内展示的百分比单调不减**：

1. **单任务钳位**：`e.0` 改为仅在 `downloaded > e.0` 时更新。已下载字节只增不减，
   吸收下载器重试清零；重下是真实发生的，但展示层不回退。`last_event` 的更新条件
   不变，stall 看门狗语义保持原样。

2. **批次高水位**：新增 `BatchProgress`（`high_water` 取历史最大值）与纯函数
   `batch_percent`。`batch_percent` 在 `done >= total` 时返回 1.0，保证批次结束封顶
   100%；其余情况返回 `Σdl / Σtot` 并钳到 1.0，由 `BatchProgress` 吸收分母增长带来的
   回退。分母增长本身是真实信息（确有更多文件要下），但展示层不回退。

两者合起来覆盖两处独立成因：单任务钳位治「分子清零」，高水位治「分母增长」。

**有意不做**：

- 不把分母改成「批次总字节」——批次入队时各文件大小未知（需逐个 HEAD 探测），
  引入探测会拖慢启动且与现有 `host_probe` 缓存策略冲突。
- 不改 `downloadThreads` 默认值（64）。实测并发 64 会触发较多龟速重试，但属调参
  而非缺陷，不同网络最优值不同，保留用户可调。
- 不接入 BMCLAPI 作为 assets 兜底：实测该节点 5 次请求 3 次完全失败（status=0），
  接入会引入新故障源。

## 备选方案

### 方案 仅做单任务钳位（治分子）
- 优点：改动更小
- 缺点：分母增长导致的「99% 跳回 60%」仍在，只解决一半症状
- 为何不选：两处成因独立，必须同时治

### 方案 分母改为批次总字节
- 优点：语义最正确，百分比单调且可解释
- 缺点：批次入队时文件大小未知，需为每个文件增加 HEAD 探测；慢网络下探测本身
  就是主要耗时（实测 HEAD 0.17–4.3s），得不偿失
- 为何不选：成本高于收益，高水位已能消除可感知的回退

### 方案 前端做进度单调化
- 优点：不动后端
- 缺点：`current_file_progress` / `completed_files` 由后端合成后经 SSE 推送，
  前端无法区分「真实回退」与「批次切换」；且下载中心与安装进度两条链路都要改
- 为何不选：职责应在产生该数值的聚合点收口

## 影响

- `src-backend/qomicex-backend/src/services/install_service.rs`
  （`download_batch` 进度单调化 + `batch_percent` / `BatchProgress` + 回归测试）
- 无 API 变更，无前端改动；`download_batch` 被实例安装与整合包在线安装共用，
  两条链路同时受益
- 仅影响**展示层**百分比与单文件进度，不改变下载行为、并发度或重试策略
