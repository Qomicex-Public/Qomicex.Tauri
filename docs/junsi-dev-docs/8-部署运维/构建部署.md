# 构建与部署

## 开发环境

### 前置要求

| 组件 | 版本要求 | 用途 |
|:---|:---|:---|
| Node.js | >= 18 | 前端构建 |
| .NET SDK | 10.0 | 后端构建 (NativeAOT) |
| Rust | latest stable | Tauri 桌面外壳 |
| PowerShell | 5.1+ (Windows) / pwsh (其他) | 构建脚本 |

### 前端开发

```bash
# 纯前端开发 (端口 1420)
npm run dev

# 构建 (tsc → vite build，类型错误会失败)
npm run build
```

### 后端开发

```bash
cd src-backend/Qomicex.Launcher.Backend.Neo
dotnet run    # 端口 5000
```

Vite 开发服务器将 `/api/*` 代理到 `localhost:5000`。

### Tauri 桌面开发

```bash
npm run tauri dev    # 启动 Tauri 窗口 + 前端 + 后端
```

## 构建系统

### GitHub Actions CI/CD

配置文件: `.github/workflows/release.yml`

### 触发方式

1. **workflow_dispatch** — 手动触发，填写版本参数
2. **release:published** — GitHub Release 发布时从 tag 解析版本

### 版本格式

```
v<major>.<minor>.<patch>-<type><序数>.<补丁/构建>
```

| 类型 | 序数来源 |
|:---|:---|
| release | 手动输入 |
| beta | 手动输入 |
| alpha | 自动取当天日期 + 当日构建序号 |

### 构建参数

| 参数 | 说明 | 可选值 |
|:---|:---|:---|
| `buildPlatform` | 目标平台 | `windows`, `linux`, `macos`, `loongarch64`, `all` |
| `linuxBundles` | Linux 打包格式 | `appimage`, `deb`, `rpm` 组合 |
| `macosArch` | macOS 架构 | `both`, `arm64`, `x64` |
| `windowsArch` | Windows 架构 | `both`, `arm64`, `x64` |
| `licenseRequired` | 启用许可证验证 | boolean |
| `prerelease` | 标记为 Pre-release | boolean |

### 构建流程

```
1. 解析版本参数 → 构造标准版本号
2. 按 RID 发布后端 (dotnet publish -p:LicenseRequired=<bool>)
3. 后端二进制嵌入 src-tauri/binaries/
4. Tauri 构建 → 生成平台安装包
```

### 本地 Release 构建

```bash
# Windows
pwsh ./build-release.ps1
```

### LoongArch64 交叉编译

loongarch64 产物在 x86_64 runner 上交叉编译，不使用 QEMU 模拟。

**工具链**：官方 [loong64/cross-tools](https://github.com/loong64/cross-tools) release，
固定 tag（`20260912`）+ `mainline` 变体。该变体 glibc 2.41 与 loong64 Debian
trixie 的 `libc6` 2.41 一致；`stable` 变体 glibc 2.38 低于宿主系统库，链接期会缺符号。
工具链自带完整 glibc sysroot（`crt1.o` / `libc.so` / 动态链接器），系统库 deb 解进同一棵树。

**sysroot 构建**：`scripts/build-loong64-sysroot.sh`

- 原生库（`libwebkit2gtk-4.1-dev` 等）无 x86_64 版本，从 `mirrors.loong64.com` 的
  loong64 Debian 源解包出 sysroot。
- deb 的 `.pc` 归属**不能靠猜包名**：实测 `glib-2.0.pc` 属于 `libgio-2.0-dev` 而非
  `libglib2.0-dev`。脚本用官方 `Contents-loong64.gz` 建立 文件→包 的确定性映射，
  缺 `.pc` 时反查属主并补包。
- 关键 `.pc` 全齐才通过（`webkit2gtk-4.1`、`gtk+-3.0`、`libsoup-3.0`、`openssl` 等），
  缺失即退出，不让错误拖到 cargo 阶段才暴露。
- 解包时剔除 `usr/share/{doc,man,locale,info}`：全量保留会让 sysroot 膨胀到 GB 级。

**关键环境变量**（`release.yml` 中 `Export cross-compile environment` 步骤导出）：

| 变量 | 作用 |
|:---|:---|
| `CARGO_TARGET_LOONGARCH64_UNKNOWN_LINUX_GNU_LINKER` | 指向交叉 gcc；不设会链到宿主 `cc`，产出 amd64 目标文件 |
| `PKG_CONFIG_SYSROOT_DIR` | 让 `-sys` crate 找到 loongarch64 头文件 |
| `PKG_CONFIG_LIBDIR` | 只搜 sysroot 内的 `.pc` |
| `PKG_CONFIG_PATH`（置空） | 防止回落到宿主 `/usr/lib/x86_64-linux-gnu/pkgconfig` |

**产物校验**：`Assert loongarch64 artifacts` 步骤从 deb 内取出启动器 ELF 断言
`LoongArch`，并用 `readelf` 确认 sysroot 内 `libwebkit2gtk-4.1.so.0`、
`libgtk-3.so.0`、`libsoup-3.0.so.0` 也是 LoongArch——交叉链接最危险的失败模式
是把宿主 amd64 的 `.so` 链进来。

本地复现 sysroot 构建：

```bash
TOOLS_DIR=/opt/x-tools SYSROOT=/tmp/loong64-sysroot bash scripts/build-loong64-sysroot.sh
```

> 注：`buildPlatform=all` 不触发 loongarch64 作业，且该作业不在 `release.needs` 中，
> 产物目前无法随发布出货。属发版矩阵设计问题，见 issue #210。
